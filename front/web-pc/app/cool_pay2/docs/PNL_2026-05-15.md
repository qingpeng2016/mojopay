## 一、改造背景

旧 PNL 公式存在两个口径缺陷：

1. **Poly 侧用接口请求金额，不是真实成交金额**
   `source_trader_records.trade_amount` 是我们向 Poly 下单时记录的请求金额。Poly 实际撮合时存在**内扣手续费 + 撮合点位**等差异，真实扣款/到账金额跟请求金额不一致（典型差 0.2~0.3 / 10）。继续用 `trade_amount` 算 PNL 会系统性偏低或偏高。

2. **没有计入结算盈亏**
   预测市场到期结算时，赢家 token 每份 = $1，输家 token 每份 = $0。
   我们持有的"未对冲份额"在结算时会有真实的盈亏发生，但旧公式完全不算这一项。

Dylan 在 trader / mapping 表上加了 4 个新字段配合新公式：

| 表 | 字段 | 类型 | 用途 |
|---|---|---|---|
| `source_trader_records` | `real_trade_amount` | `decimal(28,8)` | Poly 真实成交金额（扣除内部手续费后） |
| `source_trader_records` | `amount_finalized` | `tinyint(1)` | 是否已回填 `real_trade_amount`，回填脚本异步跑 |
| `market_mapping_config` | `source_winning_token_id` | `varchar(160)` | 市场结算赢家 Poly token；未结算市场为空串 |
| `market_mapping_config` | `source_winning_outcome` | `varchar(255)` | 赢家 outcome 文字描述（如 yes / no），辅助信息 |

> 注：`market_mapping_config.is_manual_update` 是 Dylan 的运营标志，跟 PNL 算法无关。

## 二、新 PNL 公式

```
PNL = (FG_sell_amount − FG_buy_amount − Poly_buy_real + Poly_sell_real)          ← Part 1: 已对冲差价
    + (Poly_isWon_BUY_qty − Poly_isWon_SELL_qty − FG_isWon_SELL_qty + FG_isWon_BUY_qty)  ← Part 2: 结算差价
```

### 2.1 字段对照表

| 公式变量 | 物理表 | 物理字段 | 过滤条件 |
|---|---|---|---|
| `FG_sell_amount` | `target_trader_records` | `trade_amount` | `order_side='SELL' AND status='FILLED'` |
| `FG_buy_amount` | `target_trader_records` | `trade_amount` | `order_side='BUY' AND status='FILLED'` |
| `Poly_sell_real` | `source_trader_records` | **`IF(real_trade_amount=0, trade_amount, real_trade_amount)`** | `order_side='SELL' AND status='FILLED'` |
| `Poly_buy_real` | `source_trader_records` | **`IF(real_trade_amount=0, trade_amount, real_trade_amount)`** | `order_side='BUY' AND status='FILLED'` |
| `Poly_isWon_BUY_qty` | `source_trader_records` | `trade_quantity` | `order_side='BUY' AND status='FILLED'` AND **(market_config_id, source_token_id) 在赢家集合内** |
| `Poly_isWon_SELL_qty` | 同上 | 同上 | 同上但 `order_side='SELL'` |
| `FG_isWon_BUY_qty` | `target_trader_records` | `trade_quantity` | `order_side='BUY' AND status='FILLED'` AND **(market_config_id, target_token_id) 在赢家集合内** |
| `FG_isWon_SELL_qty` | 同上 | 同上 | 同上但 `order_side='SELL'` |

### 2.2 关键设计决策（产品决定）

- **`real_trade_amount = 0` 时兜底用 `trade_amount`**（产品 2026-05-15 当天决策变更）
  - SQL 表达式：`IF(real_trade_amount = 0, trade_amount, real_trade_amount)`
  - 含义：Dylan 的回填脚本未跑完前，`real_trade_amount` 默认 0；改用 `trade_amount`（请求金额）作近似值，避免 PNL 出现"FG 侧扣了、Poly 侧没扣"的虚高数字
  - 已回填行（`amount_finalized=1` 时 `real_trade_amount` 非 0）继续用真实金额——回填越完整数字越准
  - 边界 case：若某笔真实成交金额本来就 = 0（罕见），会被误判为"未回填"用 trade_amount 兜底；可接受
- **不扣手续费**（去掉旧公式的 `- SUM(fee_amount)`）：Poly 那边手续费内扣已经反映在 `real_trade_amount` 里了；兜底用 `trade_amount` 时不含 fee 也接受（小幅误差）
- **未结算市场不参与 Part 2**：`source_winning_token_id` 为空串的市场，不在赢家集合，自动跳过

### 2.3 输家 token 的语义说明（容易误解）

公式 Part 2 只统计**赢家** token 的份额差。但 **输家 token 不是"被忽略了"**——它通过 Part 1 间接体现亏损：

```
我们在输家 token 上净买入 $X       →  Part 1 给 −$X（FG_buy 反向贡献）
我们在输家 token 上净卖出 $Y       →  Part 1 给 +$Y（FG_sell 正向贡献）
                                      Part 2 = 0（不算）
```

合理性：
- 输家结算后每份 = $0
- 我们之前为它付出的钱（净买入额）就是已经"打水漂"的钱 → Part 1 里扣下来
- 我们之前从客户那收的钱（净卖出额）落袋为安，结算后无需偿付 → Part 1 里加上来

## 三、is_won 判定逻辑

### 3.1 Poly 侧（`source_trader_records`）

直接对比 trader 行的 `source_token_id` 与 mapping 行的 `source_winning_token_id`：

```sql
trader.source_token_id = market_mapping_config.source_winning_token_id
```

### 3.2 FG 侧（`target_trader_records`）

**没有直接字段**。`market_mapping_config` 里**没有** `target_winning_token_id` 这种字段（Dylan 明确说过后续也不会加）。

需要走 `token_id_mapping` JSON 反查：

```
1. 从 mapping 拿 source_winning_token_id（Poly 赢家）
2. 解析 token_id_mapping JSON，结构：
   [
     {"sourceTokenId": "...", "targetTokenId": "...", "type": "..."},
     {"sourceTokenId": "...", "targetTokenId": "...", "type": "..."}
   ]
3. 找到 sourceTokenId 等于 source_winning_token_id 的那一对
4. 取它的 targetTokenId 即 FG 赢家
```

实现：见 `app/cool_pay2/trait/PnlCalcTrait.php::getWinningTokens()`。

### 3.3 SQL 反查注意事项

如果手写 SQL 用 `JSON_TABLE`：MySQL 8 的 JSON_TABLE 抽出来的列默认 collation 是 `utf8mb4_0900_ai_ci`，而 `market_mapping_config.source_winning_token_id` 列是 `utf8mb4_unicode_ci`，直接 `=` 比较会报：

```
[1267] Illegal mix of collations (utf8mb4_0900_ai_ci, IMPLICIT) and (utf8mb4_unicode_ci, IMPLICIT) for operation '='
```

必须显式加 COLLATE：

```sql
JSON_TABLE(token_id_mapping, '$[*]' COLUMNS (
    stok VARCHAR(160) PATH '$.sourceTokenId',
    ttok VARCHAR(160) PATH '$.targetTokenId'
)) j
WHERE j.stok COLLATE utf8mb4_unicode_ci = m.source_winning_token_id
```

代码层用 PHP `json_decode` 解析 + 在 PHP 内对比，**完全绕开了这个坑**，所以应用代码不受影响——只有手写 SQL 排查时要注意。

## 四、代码改动清单

### 4.1 新文件：`app/cool_pay2/trait/PnlCalcTrait.php`

提供两个 protected 方法给 controller 复用：

| 方法 | 用途 |
|---|---|
| `getWinningTokens(?array $mcIds = null): array` | 拿一组（或全部已结算）market 的赢家 token，返回 `[market_config_id => ['poly' => ..., 'fg' => ...]]`。包含 token_id_mapping JSON 解析 |
| `sumIsWonQtyDiff(...)` | 在 trader 表上聚合赢家行的 `SUM(BUY qty) − SUM(SELL qty)`，用 `(market_config_id, token_col) IN ((?,?), ...)` 元组 IN 精准过滤。支持可选 GROUP BY（market / outcome / DATE / HOUR 都用得上） |

详见 trait 文件头注释。

### 4.2 修改：`app/cool_pay2/controller/DataReport.php`

`buildStats()` 里 `$pnl30` 整段重写：

```php
// Part 1
$fgRow   = Db::name('target_trader_records')->...->find();   // 注意：不用 ->value('xxx')，会覆盖 fieldRaw
$fgNet   = (float)($fgRow['net'] ?? 0);
$polyRow = Db::name('source_trader_records')->...->find();
$polyNet = (float)($polyRow['net'] ?? 0);

// Part 2
$winners = $this->getWinningTokens();
$polyTuples = $fgTuples = [];
foreach ($winners as $mcId => $w) { ... }
$polyQty = array_sum($this->sumIsWonQtyDiff('source_trader_records', 'source_token_id', $polyTuples, $start30));
$fgQty   = array_sum($this->sumIsWonQtyDiff('target_trader_records', 'target_token_id', $fgTuples,   $start30));

$pnl30 = $fgNet + $polyNet + $polyQty + $fgQty;
```

**踩坑提醒**：ThinkORM 的 `->value('xxx')` 会**重写整个 SELECT 子句**为 `SELECT xxx FROM ...`，把 `->fieldRaw()` 设的聚合表达式扔掉。配合 `fieldRaw('... AS net')->value('net')` 用必出错（`net` 不是真列）。统一用 `->find()` 读结果数组 `['net']`。

## 五、最大单市场亏损：粒度变更（PRD 明确点名）

| | 旧 | 新 |
|---|---|---|
| 聚合粒度 | `target_group_id`（market 级） | `target_token_id`（outcome 级） |
| 显示 ID | market id（短字符串） | token_id（**长串，需截短**） |
| 业务意义 | 哪个市场亏得最多 | **哪个 outcome 亏得最多** |

为什么改：一个 market 通常有 yes / no 两个 outcome（输家 + 赢家）。市场聚合会让两个 outcome 的盈亏互相抵消，看着像微亏；真实的"亏损大头"是输家 outcome 那一个，按 outcome 拆开才能定位。

**真实案例对比**（dev 环境同一时间范围）：

| 公式 | 最大单市场亏损 |
|---|---|
| 旧（market 粒度） | $-2.66 |
| 新（token 粒度） | **$-12.64**（token=2006392，市场=Map Handicap: EF vs Pcific Esports，输家 = Eternal Fire 这一边） |

## 六、烟测与反算（验证算法正确性）

测试库 `172.16.39.253/mm`，时间范围 2026-04-15 ~ 2026-05-15：

| 指标 | 旧公式 | 新公式 | 差值 |
|---|---|---|---|
| 总 PNL | $2,097.16 | $2,802.69 | +$705.53 |
| 盈利市场数 | 20 (87.0%) | 22 (95.7%) | +2 |
| 亏损市场数 | 3 (13.0%) | 1 (4.3%) | −2 |
| 最大单市场亏损 | $-2.66（market 粒度） | $-12.64（token 粒度） | 粒度变更，不可直接对比 |

### 6.1 总 PNL 差值反算

```
旧 = FG_net + Poly_net − fee_total = 2930.93 + (-793.80) − 39.96 = 2097.17 ✓
新 = FG_net + Poly_real_net + Part2_poly + Part2_fg
   = 2930.93 + 0 + 1216.53 + (-1344.77)
   = 2802.69 ✓
差值 = -Poly_net + fee_total + (Part2_poly + Part2_fg)
     = 793.80 + 39.96 + (-128.24)
     = 705.52 ≈ +$705.53 ✓
```

数据出处（在测试库实测）：
- `SUM(trade_amount) - SUM(trade_amount) sign-adjusted` from source_trader_records → poly_net=-793.80, fee_total=39.96
- 已结算市场数 = 1742（`source_winning_token_id` 非空）
- Part 2 Poly = +1216.53；Part 2 FG = -1344.77

### 6.2 最大单市场亏损反算（token=2006392）

业务背景：market 536 已结算（`source_winning_token_id = 54274...734994`），`token_id_mapping` 反查得到 FG 赢家 = `2006393`（Pcific Esports）→ token `2006392`（Eternal Fire）是**输家**。

```
PNL[token=2006392]
  = Part 1 FG_net (SUM(SELL amount − BUY amount))
  + 0 (Poly real_amount 未回填)
  + 0 (输家 token 不入 Part 2)
  = -12.6360
```

实测查询确认：`part1_fg_amount = -12.6360, part2_fg_qty = 0.0000` ✓

业务含义：我们在 Eternal Fire 这边净买入了 $12.64 的份额，市场结算后 Eternal Fire 输了，份额归零，$12.64 实际亏损落地。

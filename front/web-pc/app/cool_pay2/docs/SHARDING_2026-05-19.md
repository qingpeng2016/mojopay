# cool_pay2 多分片改造（v2026-05-19）

**项目**：fg-marketmaker-mis · cool_pay2 模块
**触达页面**：数据报表、数据洞察、做市机器人详情
**外部依赖**：fgmm-runtime `release/1.0.0-beta+20260515` 分支的分片路由表

---

## 一、背景

runtime 项目（Go）2026 年 5 月把对冲策略从单库扩成水平分片：

```
fgmm_runtime (控制库, 单实例 172.16.39.211)
├─ sys_sharding_config      ── 业务分片清单（mm_0/mm_1/.../mm_N）
└─ sys_market_sharding_index── condition_id → (target_group_id, sharding_id) 永久绑定

业务分片库（同 schema 不同实例）
├─ mm_0 @ 172.16.39.211/uat_mm  (老库, weight=1, ~9 个新市场, 大量历史市场)
└─ mm_1 @ 172.18.47.151/uat_mm  (新库, weight=100, ~1700 个新市场)
```

OMS 入口新市场分配：在 `status=1 AND accept_new_market=1 AND weight>0` 的库里按 `weight` 做加权确定性 hash（`fnv64a + splitmix64`）选库，并在 `sys_market_sharding_index` 上 `INSERT IGNORE` 占位锁定。**同 target_group_id 永远绑同一个分片**。

实测分布（2026-05-19）：
- mm_0：9 个新市场 + 25804 个 sharding 前的老市场（不在 sys_market_sharding_index 里）
- mm_1：1670 个新市场（全在 sys_market_sharding_index 里）

PHP admin 之前只连 mm_0，**所有数据展示都漏了 mm_1 上的 99% 新市场**。本次改造让 admin 跨片聚合读 + 同步写。

---

## 二、为什么不用 Mycat

runtime 的选库规则（加权确定性 hash + condition_id 永久占位）不是 Mycat 内置的任何一种规则。要让 Mycat 知道一个新 target_group_id 应该路由到哪一片，必须：
- 写 Java 自定义 sharding 插件，规则与 runtime 行为对齐；或
- 在 Mycat 里手抄规则——两边状态一旦走偏，新市场就路由错分片，账永远对不上。

而 runtime 控制库（`sys_sharding_config` + `sys_market_sharding_index`）**本身就是路由真相**。PHP admin 直接读它就行，不需要再造一份。所以走"应用层 fan-out + 控制库做路由真相源"。

## 三、表归属与路由策略

| 表 | 物理位置 | admin 读策略 | admin 写策略 |
|---|---|---|---|
| `source_trader_records` | 业务分片（按市场分） | fan-out 求和 / fan-out 分页 | 不写 |
| `target_trader_records` | 业务分片（按市场分） | fan-out 求和 / fan-out 分页 | 不写 |
| `market_mapping_config` | 业务分片（按市场分） | fan-out | 单片定向（按 target_group_id 路由） |
| `config_trade` | 业务分片（**所有片副本一致**） | 任一片读（默认 mm_0） | **fan-out 同步写所有 status=1 分片** |
| `accounts` | 业务分片（所有片副本一致） | 任一片读 | 不写（admin 不动这个表） |
| `sys_sharding_config` | 控制库 | 5min TTL 缓存 | 不写 |
| `sys_market_sharding_index` | 控制库 | 单条命中查询 | 不写 |

字段级别注意：
- `market_config_id`（trader 表 + market_mapping_config.id）是**分片本地自增**，跨片不可比；任何"先查 mc_id 再用 mc_id 过滤"的代码必须在同一个分片闭包内完成，**绝对不能跨片传递 mc_id**
- `target_group_id` 是全局唯一字符串，跨片安全
- trader 表筛选用 `target_group_id IN (...)`，**不要**用 `market_config_id IN (...)`

## 四、ShardManager API

文件：`app/cool_pay2/service/ShardManager.php`

**路由 / 连接管理**
```php
ShardManager::getActiveShards(): array
    // 返回 [shardId => ['id','name','host','port','database','username','password','weight','accept_new_market']]
    // 5min TTL 缓存
    // 两层过滤（按顺序）：
    //   1) env SHARD_EXCLUDE_IDS=3,4 显式排除（应急逃生口，正常不设）
    //   2) filterByCompatibility 自动探测：每片走 information_schema 查
    //      `source_trader_records` 表存在性 —— 不存在则跳过（说明不是对冲策略分片）
    //      探测失败（连接/权限错）保留分片，让真实 fan-out 暴露问题（不静默吞片）
    //   见下方"自动探测兼容性"说明

ShardManager::conn(int $shardId): string
    // 拿到分片对应的 ThinkPHP 连接名（首次调用自动注册到 Db facade）。连接名规则：db_shard_<id>

ShardManager::getShardIdForMarket(string $targetGroupId): ?int
    // 单市场路由：1) sys_market_sharding_index 查；2) 未命中 fan-out market_mapping_config 兜底；3) 进程内缓存
```

**跨片读写**
```php
ShardManager::fanOutRead(callable $cb): array
    // 每片各执行 $cb($connName, $shardInfo)，返回 [shardId => result]
    // 容错：env SHARD_SKIP_UNREACHABLE=1 时单片报错记日志 + 跳过（仅本地 docker 用）
    // prod 默认不设这个 env —— 任一片失败 → 抛异常 → admin 看到 500（聚合不完整就直接告警）

ShardManager::fanOutSumByKey(callable $cb): array
    // fanOutRead 的便捷版：每片返回 [key => 数值]，跨片合并同 key 求 sum，最终返回 [key => Σ value]
    // 典型用法：按 DATE / target_group_id / target_token_id 跨片聚合数值

ShardManager::fanOutWriteInTx(callable $cb): array
    // **2PC 强原子写**：phase 1 每片 startTrans+exec，全 OK 才 commit all，否则 rollback all
    // 任一片失败 → 所有 per_shard.ok=false（含 atomic_status = rolled_back / commit_failed / partial_committed）
    // 调用方按 array_filter(!ok) 检查即得强原子保证：失败 = 全部回滚

ShardManager::fanOutInsert(string $table, array $data): array
    // 跨片 INSERT 一行 A 类全局配置（不对齐 id；UPDATE/DELETE 按业务唯一键）
    // 内部调 fanOutWriteInTx → 自动 2PC，任一片失败整体回滚

ShardManager::existsAcrossShards(string $table, array $where): array
    // 跨片业务键存在性检查（A 类 add/edit 之前 pre-check，避免可预测的失败再触发回滚）
```

PDO 连接参数 `PDO::ATTR_TIMEOUT => 5`，避免本地 docker 触达不到某分片时卡 60s+。

### 自动探测兼容性（filterByCompatibility）

**触发场景**：dev/test 的 `sys_sharding_config` 里**混入了非对冲策略的分片**。

具体来说，dev 环境同一个控制库现在登记着 3 个分片：

| id | name | schema | 用途 | 跨片表结构是否兼容 cool_pay2 |
|---|---|---|---|---|
| 1 | mm | mm | 对冲策略 | ✅ 完整一致 |
| 2 | mm1 | mm1 | 对冲策略 | ✅ 完整一致 |
| 3 | self_mm | fgmm_self_mm | **自做市策略**（独立项目） | ❌ 缺 source_trader_records / target_trader_records / target_group_id 字段等 |

如果 cool_pay2 的 fan-out 不区分地打到 self_mm，会触发 `Table 'fgmm_self_mm.source_trader_records' doesn't exist` 之类的 SQL 错；落到 `fanOutWriteInTx` 上等于 phase 1 失败 → 整体回滚 → 用户在 UI 上看到"更新失败"。

**判定规则**（`ShardManager.php` 第 122 行 `filterByCompatibility`）：

```text
对每个 status=1 分片：
  SELECT COUNT(*) FROM information_schema.tables
   WHERE table_schema = <分片 database>
     AND table_name   = 'source_trader_records'

  count = 0           → 跳过该分片（不是对冲策略分片），error_log 记一行
  count > 0           → 保留
  查询抛异常（超时/权限错）→ **保留**，让真实 fan-out 暴露具体错（避免静默吞分片）
```

哨兵表选 `source_trader_records`：cool_pay2 所有跨片操作要么直接读它，要么间接依赖（market_mapping_config 也只在对冲分片有数据）。它存在 → 这片就完整支持 cool_pay2 的全部 fan-out 路径。

**缓存语义**：探测结果跟 `$shardsCache` 一起缓存（5 min TTL）；不是"永久标记"——下次缓存过期时会重探。新分片上线只要 schema 完整就自动被纳入；老分片把 schema 改全也会自动恢复。

**`SHARD_EXCLUDE_IDS` 和自动探测的关系**：两层叠加。`SHARD_EXCLUDE_IDS` 先过（显式黑名单 / 临时屏蔽用），filterByCompatibility 后过（schema 自适应）。正常 dev / prod 都不需要设 `SHARD_EXCLUDE_IDS` —— 自动探测已经覆盖了 self_mm 这类异构分片的场景。这个 env 留着只是逃生口，比如临时屏蔽一片做演练。

**两个易错点**：
1. **不要换 `REQUIRED_TABLE` 常量**而不调清 cache —— 改完要么重启容器要么 `php think clear`，否则进程内 `$shardsCache` 还是旧探测结果。
2. **不要把 `filterByCompatibility` 改成调 `self::conn($sid)`**：`conn()` 内部会调 `getActiveShards`，而 `getActiveShards` 此时还没把结果写入 cache，会无限递归。必须走 `self::registerConnection($sid, $info)`（仅注册连接，不查 cache）。`registerConnection` 是 v1.9 从 `conn()` 抽出来的私有 helper 就是为了这个。

**验证**：

```bash
# 不设 SHARD_EXCLUDE_IDS，跑自测 —— 看到 "shard 3 (self_mm @ ...) 自动跳过" 且 count=2
docker exec fg-mis-local php /var/www/html/think shard:test
```

输出片段：
```
[ShardManager] shard 3 (self_mm @ 172.16.39.253/fgmm_self_mm) 自动跳过：schema 缺 source_trader_records（不是对冲策略分片）
[OK]   1.1 拿到至少 1 个分片  →  count=2
```

## 四点五、PnlCalcTrait 共用助手（写新页面前必看）

文件：`app/cool_pay2/trait/PnlCalcTrait.php`。**任何"在 trader/market_mapping_config 上算 PNL"的新页面都应该走这套助手，不要再手写 Part1/Part2 SQL。**

```php
// 三个 SQL 表达式常量（fieldRaw 用）
PnlCalcTrait::PART1_FG_NET_EXPR        // FG 净额 SUM(SELL trade_amount − BUY trade_amount)
PnlCalcTrait::PART1_POLY_NET_EXPR      // Poly 净额（real_trade_amount 兜底）
PnlCalcTrait::PART2_BUY_SELL_QTY_EXPR  // Part 2 数量差 SUM(BUY qty − SELL qty)（外侧加 isWon 行过滤）

// 单分片完整 PNL（Part1+Part2，返回 fgNet/polyNet/polyQty/fgQty/total）
$this->buildShardPnl(string $conn, ?string $startTs, ?string $endTs, array $extra = []): array

// 单分片按 $groupCol 分组的 PNL（target_group_id / target_token_id / DATE(updated_at) / HOUR(updated_at)）
$this->buildShardPnlByGroup(string $conn, string $groupCol, ?string $startTs, ?string $endTs, array $extra = []): array
    // 返回 [groupKey => 该 key 的 PNL 合计]

// extra 支持 key：
//   target_account_id / source_account_id：账户过滤
//   target_group_id：scalar 或 string[]（全局键，跨片安全）
//   mc_ids_local：本片上的 market_config_id 集合（限制 Part 2 winners；分片本地）

// 拆 winners 为 (polyTuples, fgTuples)
PnlCalcTrait::splitWinnerTuples(array $winners): array

// 在 query 上 apply extraWhere 数组（scalar → where; array → whereIn; [] → 1=0）
PnlCalcTrait::applyExtraWhere($query, array $extra): void
```

### 新页面要算跨片 PNL 的标准模板

**指标卡片（标量）**：
```php
$perShard = ShardManager::fanOutRead(function (string $conn) use ($t0, $t1) {
    $pnl = $this->buildShardPnl($conn, $t0, $t1, ['target_account_id' => $someId]);
    return $pnl['total'];
});
$totalPnl = array_sum($perShard);
```

**按市场/outcome/日/小时分组**：
```php
$byKey = ShardManager::fanOutSumByKey(function (string $conn) use ($t0, $t1) {
    return $this->buildShardPnlByGroup($conn, 'target_group_id', $t0, $t1);
});
// $byKey = ['406912226218231355' => 12.5, '4069122..' => -3.2, ...]
```

**全局配置表（如 config_trade）跨片同步写**：
```php
$perShard = ShardManager::fanOutWriteInTx(function (string $conn) use ($updates) {
    foreach ($updates as $name => $value) {
        Db::connect($conn)->name('config_trade')
            ->where('config_name', $name)
            ->update(['value' => $value]);
    }
    return ['count' => count($updates)];
});
// 检查 array_filter(... fn($r) => !$r['ok']) 判失败片
```

**单市场写**（按 target_group_id 路由到一片）：
```php
$sid = ShardManager::getShardIdForMarket($targetGroupId);
if ($sid === null) return $this->error('找不到市场');
Db::connect(ShardManager::conn($sid))
    ->name('market_mapping_config')
    ->where('target_group_id', $targetGroupId)
    ->update($data);
```

### 跨片 PNL 计算正确性

`market_config_id` 是分片本地自增，所以脚本对**每个分片单独**：
1. 拉 source/target/mapping
2. 推导 winners（基于本片 mapping 的 `source_winning_token_id` + JSON 反查）
3. enrich 行级 `is_winner_row` / `poly_amount_used` / `is_fallback_used`
4. 行加 `__shard_name` 列

最后所有行合并到全局 source_rows / target_rows，`compute_daily_summary` 直接读 enrich 后的派生列累加——跨片 PNL = 各片 PNL 之和。

- 我方计算结果 sheet：数字是跨片合计（不区分分片）

### 需要特别注意的细节

- **`run_config.market_table_index` 是分片本地状态**（mm_0=13, mm_1=02 实测不同）—— 不是全局配置，**绝对不能跨片同步**。`MarketMappingConfig::getMarketTableIndex($conn)` 已加 $conn 参数，在 INSERT 新市场前从目标分片重读该值
- **`market_mapping_config.id` 是分片本地自增**——不可跨片传递。MarketMappingConfig 用 `findRowAcrossShards($id)` 做 fan-out 兜底定位 + `routeToRowShard($targetGroupId, $id)` 优先用全局键路由
- **A 类表 INSERT 新行**：用 `ShardManager::fanOutInsert($table, $data)`——各片独立 INSERT，跨片 id **不对齐**（各自走自己的 auto-increment）
- **A 类表 UPDATE / DELETE**：**绝对不能按 id**（id 跨片不对齐），必须按业务键。各表业务键：
  | 表 | 业务键 | DB UNIQUE? |
  |---|---|---|

### 9.3.1 跨片分页详解（5 个 controller 共用模板）

**适用页面**：DataReport / SourceTradeRecords / TargetTradeRecords / TradeRecords / MarketMappingConfig 的 `index()`。

**为什么不能用普通 `paginate()`**：
ThinkPHP `$query->paginate(15)` 发的是单条 `LIMIT (page-1)*15, 15`，只走一个数据库连接（默认 mm_0）。B 类表按 target_group_id 切到 mm_0/mm_1/mm_N，**一行只在一片**，单连接 paginate 必然漏掉其它片所有行（改造前财务对账少算 12% PNL 就是这个原因）。

**5 步算法**（以 `DataReport::index()` `controller/DataReport.php:56-92` 为参考实现）：

```
ShardManager::fanOutRead 闭包在每个 active shard 内执行：
  step 1: shard.count = COUNT(*) WHERE filters         本片满足筛选的总行数
  step 2: shard.rows  = SELECT * WHERE filters
                        ORDER BY updated_at DESC, id DESC
                        LIMIT page × pageSize          本片"前 page×pageSize 名"
                        （注意：是 LIMIT N，不是 LIMIT offset,N）

回到 PHP 主进程：
  step 3: totalCount = Σ shard.count                   全局总行数（求和）
  step 4: merged    = ⋃ shard.rows
                      usort 按 (updated_at, id) DESC 全局排序
  step 5: pageRows  = array_slice(merged, (page-1)×pageSize, pageSize)
                      Paginator::make(pageRows, pageSize, page, totalCount, ...)
```

**具体例子**：两片 mm_0/mm_1，访问第 **2 页**，pageSize=**3**。两片实际数据按 updated_at 排序：

```
mm_0 (4 行):                       mm_1 (5 行):
A0  12:00                          B0  11:55
A1  11:50                          B1  11:52
A2  11:40                          B2  11:45
A3  11:30                          B3  11:35
                                   B4  11:20
```

- Step 1：mm_0.count=4，mm_1.count=5
- Step 2：每片各取 page×pageSize = 2×3 = 6 行（不足则取全部）
  - mm_0 → `[A0, A1, A2, A3]`
  - mm_1 → `[B0, B1, B2, B3, B4]`
- Step 3：`totalCount = 4 + 5 = 9`
- Step 4：合并 + usort 排序后：`[A0, B0, B1, A1, B2, A2, B3, A3, B4]`
- Step 5：`array_slice(merged, 3, 3)` → `[A1, B2, A2]`（全局第 4-6 名）；Paginator 用 totalCount=9 渲染「共 3 页」

**完整性证明 / 为什么"每片只取 page×pageSize 行"够用**：
要进入全局前 page×pageSize 名的行，它在本片排名必然 ≤ page×pageSize（因为每片排序键和全局排序键一致）。所以每片取前 page×pageSize 行 → 合并集合 ⊇ 全局前 page×pageSize 名 → 切第 P 页（第 (P-1)*S 到 P*S-1 索引）一定准确。

**三类边界注意**：

| 项 | 说明 | 风险 |
|---|---|---|
| `filterByCompatibility` 跳过 | 探测到 schema 缺 `source_trader_records` 的片自动跳过（如 self_mm）。**正常对冲分片不会被跳过**；但若某对冲片 schema 被破坏，分页会静默丢这片的行。error_log 里"shard X 自动跳过"需要监控告警。 | 🟡 边界 |
| 深翻页内存代价 | 每片拉 page×pageSize 行进 PHP 数组。page=1000、pageSize=15 → N×15000 行内存排序。功能正确但慢。业务上用户极少深翻，可接受；如果成为瓶颈，方案是 keyset pagination（按 updated_at 游标）替代 offset。 | 🟡 性能 |
| COUNT 与 SELECT 之间的瞬时插入 | 两次 SQL 间几毫秒内的新写入，可能造成 totalCount 与本页行数微小不一致。单机分页同样问题，不是分片特有。 | 🟢 可忽略 |

**不会发生的"伪遗漏"**：
- ❌ id 跨片重复被去重：`merged[]` append 不 dedupe；id 跨片本就是本地自增，按 id 去重才是 bug
- ❌ updated_at 在两片相同丢行：usort 稳定排序 + (updated_at, id) tie-breaker，tie 情况只是顺序不定，行不会消失
- ❌ Paginator 总页数错：`ceil(totalCount/pageSize)` 用的就是跨片求和后的真实总数

**写新分页页面的代码模板**：

```php
$page = max(1, intval($get['page'] ?? 1));
$pageSize = max(1, intval($get['pageSize'] ?? 15));

$perShard = ShardManager::fanOutRead(function (string $conn) use ($get, $page, $pageSize) {
    $q = Db::connect($conn)->name('source_trader_records');
    $this->applyListFilters($q, $get);       // 本片应用筛选（不能传 mc_id 跨片）
    $count = (int)(clone $q)->count();
    $rows = (clone $q)
        ->order('updated_at', 'desc')
        ->order('id', 'desc')                // tie-breaker
        ->limit($page * $pageSize)           // 注意：limit N，不是 limit offset,N
        ->select()->toArray();
    return ['count' => $count, 'rows' => $rows];
});

$totalCount = 0; $merged = [];
foreach ($perShard as $sid => $s) {
    $totalCount += $s['count'];
    foreach ($s['rows'] as $row) {
        $row['__shard_id'] = $sid;           // 可选：B 类编辑场景透传到 view
        $merged[] = $row;
    }
}
usort($merged, static function ($a, $b) {
    $cmp = strcmp((string)($b['updated_at'] ?? ''), (string)($a['updated_at'] ?? ''));
    return $cmp !== 0 ? $cmp : (((int)($b['id'] ?? 0)) <=> ((int)($a['id'] ?? 0)));
});
$pageRows = array_slice($merged, ($page - 1) * $pageSize, $pageSize);

$result = Paginator::make($pageRows, $pageSize, $page, $totalCount, false, [
    'query' => $get,
    'path'  => '/admin.html#/cool_pay2/<your_controller>/index.html',
]);
```

### 9.4 更新路径（三层防御）

```
INSERT (A 类全局配置):
  Layer 1  existsAcrossShards(table, business_key)
              ↳ 任一片业务键已存在 → 拒绝
  Layer 3  fanOutInsert → fanOutWriteInTx (2PC)
              ↳ 各片独立 auto-id；任一片失败全回滚

UPDATE (A 类):
  → 默认分片读 originalRow 拿 origKey
  Layer 1  若 newKey ≠ origKey → existsAcrossShards(newKey)
              ↳ 新键已被占用 → 拒绝
  Layer 2  missingAcrossShards(table, keyCol, [origKey])
              ↳ 任一片缺该 key → "请先跑 SQL 初始化"（防 silent 0 affected）
  Layer 3  fanOutWriteInTx UPDATE WHERE key = origKey
              ↳ 2PC 任一失败全回滚

UPDATE (B 类 market_mapping_config):
  → 路由优先级: __shard_id (form) > target_group_id (索引) > findRowAcrossShards(id) fallback
  → 单片 UPDATE，单语句天然原子

DELETE (A 类):
  → 默认分片读 originalRow 拿 origKey
  Layer 3  fanOutWriteInTx DELETE WHERE key = origKey
              ↳ 2PC 任一失败全回滚
              ↳ missingAcrossShards 不做：DELETE 在缺片 0 affected 是幂等的，不算错
```

### 9.5 关键不变量

```
✅ target_group_id  全局唯一  → 跨片可比 / 可路由
✅ condition_id     全局唯一  → 同上
✅ token_id         (Polymarket 链上 ID)  → 全局唯一
❌ market_mapping_config.id        分片本地自增 → 绝不跨片传
❌ trader 表 id                    分片本地自增 → 绝不跨片传
❌ market_config_id                分片本地自增 → 用 (mc_id, token_id) 元组时必须同片内匹配
❌ run_config.market_table_index   分片本地状态 → INSERT 前从目标分片重读
```

### 9.6 错误处理 / 边界

| 现象 | 处理 |
|---|---|
| 单片瞬时错误（timed out/lost connection/deadlock） | fanOutWriteInTx 自动重试 1 次，per_shard.retried=true |
| 单片永久错误（SQL 错/UNIQUE 冲突） | 不重试，所有 per_shard.ok=false，事务全回滚 |
| Phase 2 commit drift（极少，2PC blind spot） | 已 commit 片标 partial_committed，error_log 记录，shard:repair 兜底 |
| fanOutRead 单片不可达（prod） | 抛异常 → 500，不会静默给部分数据 |
| fanOutRead 单片不可达（local docker） | env `SHARD_SKIP_UNREACHABLE=1` 时跳过；**prod 千万不要设这个 env** |
| A 类 UPDATE 在缺片 0 affected | missingAcrossShards 拦下，明确报"先跑 SQL"（v1.7 修） |
| B 类编辑 list 上 id 撞片 | __shard_id 透传 + form hidden 字段（v1.5 修） |
| 控制库混入异构 schema 分片（如 self_mm 自做市，无 source_trader_records） | getActiveShards 自动跳过；不需要每环境设 `SHARD_EXCLUDE_IDS`（v1.9 修，详见 §四"自动探测兼容性"） |

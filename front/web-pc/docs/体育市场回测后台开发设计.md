# 体育市场回测后台开发设计

## 1. 文档目标

本文定义 `fg-marketmaker-mis/app/backtest` 中体育市场回测后台的开发方案。后台复用现有快盘页面的交互和代码组织，但使用以下三张体育表：

- `sports_market_config`：一个具体 `market_id + outcome_id + model` 的回测配置；
- `sports_market`：该 outcome 当前最新一次铺单输入、输出及市场状态；
- `sports_placement`：每次 SO 计算的只读历史快照。

首期交付范围：

1. 体育市场配置的列表、新增、编辑、启停和删除；
2. 体育市场最新快照的列表、详情、自动刷新和 CSV 导出；
3. Primary、Mirror 两个盘口的 bids/asks 展示；
4. 市场详情中的平台参数编辑，下一轮铺单生效；
5. 体育铺单历史列表、详情和 CSV 导出；
6. 菜单、权限、本地数据库连接和验收步骤。

本方案不修改现有快盘 `Config`、`Market`、`Placement` 页面，体育功能使用独立控制器和视图，避免两种策略的字段语义相互污染。

## 2. 已有工程约定

### 2.1 技术与数据库

- 框架：ThinkPHP 6 + ThinkAdmin；
- 模块：`app/backtest`；
- 模块默认连接：`app/backtest/config/database.php` 中的 `db_f_backtest`；
- 本地连接：`conf/database-local.yaml` 中已配置 `db_f_backtest`，无需新增连接名；
- 本地运行时应确认 `APP_ENV=local`，数据库为 `fgmm_f_backtest`；
- 三张体育表与快盘表在同一个 schema 中。

所有体育控制器均直接使用：

```php
Db::name('sports_market_config');
Db::name('sports_market');
Db::name('sports_placement');
```

禁止使用默认主库连接操作这三张表，也不需要在每次查询中显式 `Db::connect('db_f_backtest')`。

### 2.2 可复用的快盘实现

体育功能参考以下文件的结构和交互：

- `app/backtest/controller/Config.php`：配置 CRUD、校验和显式级联删除；
- `app/backtest/controller/Market.php`：最新快照、JSON 盘口展示、详情自动刷新、市场参数编辑；
- `app/backtest/controller/Placement.php`：历史分页、详情、CSV 导出；
- `app/backtest/view/market/detail.html`：盘口切换、档位展示、编辑弹窗；
- `scripts/menu_backtest.sql`：菜单和授权。

只复用模式和公共样式，不让体育控制器继承或调用快盘控制器的私有方法。

## 3. 数据语义与编辑边界

### 3.1 参数生命周期

平台参数包括：

- `inventory_net_yes`：净 YES 敞口；
- `inventory_max_abs`：最大绝对持仓；
- `micro_ofi`：订单流不平衡；
- `micro_aggressive_buy`：主动买量；
- `micro_aggressive_sell`：主动卖量；
- `micro_apr`：APR；
- `micro_vpin`：VPIN；
- `micro_hhi`：HHI。

参数流转规则：

```text
sports_market_config
  │ market_generate 首次生成时复制
  ▼
sports_market
  │ placement 每轮从市场行读取并拼入 SO 输入
  ├── 当前最新值持续保留在 sports_market
  └── 每轮使用值固化到 sports_placement
```

因此后台有两类编辑：

1. 配置页编辑：修改下一次“生成新市场”时使用的初始值，不自动覆盖已经存在的市场；
2. 市场详情编辑：修改当前 `sports_market` 的运行参数，下一轮铺单读取新值，用于快速比较不同微观参数效果。

页面必须明确展示提示：

> 配置值只在生成市场时初始化。市场已经生成后，请在“体育市场信息”详情中修改运行参数。

### 3.2 不可编辑数据

- `sports_placement` 是历史证据，只读，不提供修改和删除单条记录功能；
- SO 输出、诊断数据、盘口档位和 `calc_*` 字段只读；
- `sports_market` 的身份字段、时间窗口、机器和状态不允许通过市场详情直接编辑；
- 已关闭市场默认不允许修改运行参数，避免产生不会再被消费的值。

## 5. 体育市场配置

### 5.1 列表页

页面标题：`体育市场配置`。

建议列表字段：

- ID、配置键、配置名称；
- 体育类型、市场 ID、Outcome ID、模型；
- 报价开始/结束时间；
- 净敞口、最大绝对持仓；
- OFI、主动买量、主动卖量、APR、VPIN、HHI；
- 计算间隔、运行模式、历史开始/结束时间；
- 状态、是否已生成市场、备注、更新时间；
- 操作：编辑、查看市场、删除。

查询条件：

- `config_name` 模糊匹配；
- `config_key` 模糊匹配；
- `sport_type`；
- `market_id` 模糊匹配；
- `outcome_id` 模糊匹配；
- `model`；
- `run_mode`；
- `status`；
- 从市场页跳转的精确 `id`。

列表用一次聚合查询获取是否已生成市场，禁止每一行单独查询：

```sql
SELECT sports_config_id, COUNT(*) AS cnt
FROM sports_market
WHERE sports_config_id IN (...)
GROUP BY sports_config_id;
```

### 5.2 新增与编辑表单

表单分组：

1. 基本信息：`config_key`、`config_name`、`sport_type`、`market_id`、`outcome_id`、`model`；
2. 比赛状态：`event_state`、`remaining_sec`；
3. 来源路由：`source_config`；
4. 库存参数：`inventory_net_yes`、`inventory_max_abs`；
5. 微观参数：六个 `micro_*` 字段；
6. 调度参数：`calc_interval_ms`、`run_mode`、`history_start`、`history_end`；
7. 状态与备注。

`source_config` 首期使用 JSON 文本编辑器，提供格式化按钮和示例。提交后必须先 `json_decode($value, true)` 并验证：

- 顶层是非空数组；
- 每项包含非空 `type`、`source`；
- `default_margin` 是有限非负数；
- `required` 规范化为布尔值；
- 保存时重新 `json_encode(..., JSON_UNESCAPED_UNICODE | JSON_UNESCAPED_SLASHES)`。

不直接接受前端传入的任意数据库字段，控制器使用字段白名单构造 `$save`。

### 5.3 服务端校验

必须同时做 ThinkPHP 校验和业务组合校验：

- `config_key`、`config_name`、`sport_type`、`market_id`、`outcome_id`、`model` 必填；
- `config_key` 最长 128 且唯一；
- `sport_type` 当前允许 `football`、`basketball`；
- `model` 当前允许 `pre_match`、`in_play`，若实际 SO 只支持其中一种，应与 SO 枚举同步；
- history 模式要求 `history_end > history_start`；
- `calc_interval_ms > 0`；
- `run_mode` 仅允许 `live`、`history`；
- history 模式要求历史开始和结束非空，且 `history_start <= history_end`；
- history 区间必须落在报价窗口内；
- `inventory_max_abs > 0`；
- `abs(inventory_net_yes) <= inventory_max_abs`；
- 主动买量和主动卖量不得小于 0；
- 所有微观参数必须是有限数，拒绝 `NaN`、`INF` 和空字符串；
- `status` 仅允许 0、1；
- `remark` 最长 500。

编辑时对 `config_key` 做排除当前 ID 的唯一性检查。若市场已经存在，页面对身份字段和报价窗口给出醒目提示；保存这些字段不会静默改写已有市场。

### 5.4 删除配置

删除接口必须：

- 校验 ID 和记录存在；
- 二次确认；
- 使用数据库事务；
- 按 `sports_placement → sports_market → sports_market_config` 顺序删除；
- 成功后返回配置列表地址；
- 任一步失败则整体回滚。

## 6. 体育市场信息

### 6.1 列表页

页面标题：`体育市场信息`。列表只展示高频排查字段，不把全部 JSON 展平到超宽表格。

建议字段：

- ID、配置 ID、机器名；
- 体育类型、市场 ID、Outcome ID、模型；
- 市场状态、报价状态；
- 比分、比赛状态、剩余秒数；
- Primary 最优买/卖；
- Mirror 最优买/卖；
- OFI、VPIN、净敞口/最大持仓；
- 铺单次数、计算返回码、错误摘要、计算时间、更新时间；
- 操作：详情、铺单历史。

Primary/Mirror 最优价在 PHP 中从 JSON 数组计算，不在 SQL 中拼复杂 JSON 表达式。列表查询时只读取所需字段，避免把 `input_payload`、`output_payload` 等大 JSON 全部带出。

查询条件：

- `market_id`、`outcome_id`、`request_id` 模糊匹配；
- `sports_config_id`、`id` 精确匹配；
- `sport_type`、`model`；
- `machine_name`；
- `market_status`、`quote_status`；
- `calc_code`；
- `calc_time` 范围。

状态显示：

- `pending`：未开始；
- `active`：运行中；
- `close`：已结束；
- `calc_code = 0`：计算成功；
- `calc_code != 0`：失败，并展示 `calc_msg`。

### 6.2 市场详情布局

详情页开启自动刷新，刷新周期读取对应配置的 `calc_interval_ms`，设置合理下限，例如 500ms，避免错误配置造成浏览器高频请求。

模块顺序：

#### ① 基本信息

- 市场、Outcome、体育类型、模型；
- 配置跳转、机器名；
- 报价窗口、市场状态；
- request ID、quote version；
- 输入/输出时间、计算序号、耗时、返回码和错误信息。

#### ② 两个盘口

使用按钮切换 `Primary` 和 `Mirror`。每个盘口分别显示：

- asks：按价格降序渲染，使最优卖价位于卖盘区域底部；
- bids：按价格降序渲染，使最优买价位于买盘区域顶部；
- 每档显示字符串 `price`、`size`，不得先转 float 后再格式化，避免改变 SO 输出精度。

空盘口显示“暂无档位”，非法 JSON 显示解析异常提示，但详情页仍应继续展示其他模块。

#### ③ 来源数据

将 `in_sources` 解码为表格：

- type；
- source；
- available；
- suspended；
- delay_sec；
- probability；
- margin。

同时提供复制原始 JSON 的能力。

#### ④ 比赛数据

- 已赛秒数、剩余秒数；
- 主客队比分；
- 主客队红牌；
- event state。

#### ⑤ 平台运行参数

展示并允许编辑以下字段：

- `inventory_net_yes`；
- `inventory_max_abs`；
- `micro_ofi`；
- `micro_aggressive_buy`；
- `micro_aggressive_sell`；
- `micro_apr`；
- `micro_vpin`；
- `micro_hhi`。

仅当 `market_status` 是 `pending` 或 `active` 时，在每个可编辑参数的当前值旁显示“编辑”按钮，交互与快盘 `in_q/in_q_cap` 保持一致。点击后弹出单字段输入框；页面不展示配置初始值。保存时服务端将新值与数据库中其余当前参数合并，再执行库存组合校验。

#### ⑥ 其他输入

- `previous_fair_prices`；
- `historical_volatility`；
- `slippage_estimate`；
- 完整 `input_payload`，折叠展示并支持复制。

#### ⑦ 输出诊断

- source count；
- data confidence；
- reference margin；
- spread used；
- inventory usage；
- micro spread multiplier；
- alerts；
- quote status/reason；
- 完整 `output_payload`。

### 6.3 保存市场参数接口

接口：`POST /backtest/sports_market/saveParam.html`。

输入：

```json
{"id": 1, "field": "micro_ofi", "value": 0.12}
```

服务端处理：

1. `field` 只允许上述八个字段；
2. 查询市场存在且状态为 `pending` 或 `active`；
3. 执行与配置页一致的数值和库存组合校验；
4. 使用带状态条件的更新，避免查询后市场已经关闭：

```php
$affected = Db::name('sports_market')
    ->where('id', $id)
    ->whereIn('market_status', ['pending', 'active'])
    ->update($save);
```

5. `affected = 0` 时重新查询，区分“值未变化”“市场不存在”“市场已关闭”；
6. 返回 JSON 成功消息，并提示预计下一轮生效时间；
7. 不更新配置表、不修改铺单历史。

首期只有三张业务表，不新增参数修改日志表。接口应至少写应用审计日志，包含管理员 ID、市场 ID、修改前值、修改后值和请求 IP；后续如有强审计需求再增加专用表。

### 6.4 Go 回测服务并发前置修改

这是市场参数编辑可靠生效的必要条件。

当前 Go 服务 `sports_market/model/repo.go` 的 `snapshotUpdateColumns()` 会在每次铺单完成时更新：

```text
micro_ofi
micro_aggressive_buy
micro_aggressive_sell
micro_apr
micro_vpin
micro_hhi
inventory_net_yes
inventory_max_abs
```

这些字段在 placement 阶段不会由 SO 修改，因此不应随计算结果重复写回。否则会发生：

```text
Go 读取旧市场参数
  -> 管理员在 PHP 保存新参数
  -> Go 用旧对象更新整份 snapshot
  -> 新参数被旧值覆盖
```

开发后台前，应从 `snapshotUpdateColumns()` 中移除上述八列。市场首次生成仍由 `MarketRepo.Ensure()` 写入初始值；每次 `sports_placement` 仍会记录该轮实际使用的参数；下一轮查询市场时即可稳定取得后台新值。

不建议通过 PHP 加锁等待 Go，也不建议把配置表当作运行时参数表。

## 7. 体育铺单历史

### 7.1 列表页

页面标题：`体育铺单历史`，只读。

建议字段：

- ID、市场 ID、配置 ID、计算序号；
- 体育类型、市场 ID、Outcome ID、模型；
- request ID；
- 市场状态、报价状态；
- 比分和剩余时间；
- 本轮 OFI、VPIN、净敞口/最大持仓；
- Primary/Mirror 最优买卖价；
- 返回码、错误摘要、计算耗时、计算时间；
- 详情链接。

查询条件：

- `sports_market_id`、`sports_config_id`、`calc_seq`；
- `market_id`、`outcome_id`、`request_id`；
- `sport_type`、`model`；
- `quote_status`、`calc_code`；
- `calc_time` 范围。

从市场详情点击“铺单历史”时携带 `sports_market_id`。从历史详情点击市场 ID 时跳转体育市场详情，而不是快盘页面。

### 7.2 历史详情

复用体育市场详情的展示结构，但具备以下差异：

- 不自动刷新；
- 不显示参数编辑按钮；
- 标题展示 `calc_seq` 和 `request_id`；
- 所有内容来自 `sports_placement` 自身，不能 join 当前市场覆盖历史字段；
- 失败快照可能没有盘口和输出字段，页面仍需完整展示输入与 `calc_msg`。

为避免市场详情和历史详情复制大量解析代码，建议新增模块内服务：

```text
app/backtest/service/SportsSnapshotPresenter.php
```

职责仅包括：

- JSON 安全解码；
- 盘口排序；
- 数值去尾零；
- 毫秒时间戳与 datetime 格式化；
- 最优价计算；
- 输入、诊断字段标签定义。

控制器负责查询、权限和响应，Presenter 不执行数据库写入。

## 8. JSON、时间和数值展示

### 8.1 JSON

需要解码的列：

```text
source_config
in_sources
previous_fair_prices
primary_bids
primary_asks
mirror_bids
mirror_asks
alerts
input_payload
output_payload
```

统一安全规则：

- 空值返回空数组或空对象；
- `json_decode` 失败时保留原始文本并设置解析错误标志；
- 模板不使用 `raw` 输出外部 JSON；
- 复制按钮的数据通过安全编码属性或 JS 变量传递，避免引号破坏 HTML；
- 列表不展开大 JSON，详情按需展示。

### 8.2 时间

- `datetime(3)` 展示到毫秒或秒应全站统一；建议详情保留毫秒、列表显示到秒；
- `input_timestamp_ms`、`output_timestamp_ms` 同时展示原始毫秒值和格式化时间；
- PHP 与 MySQL 时区必须与回测服务的业务约定一致；不能简单把历史虚拟时间解释为页面访问时间。

### 8.3 Decimal

- 普通参数可沿用快盘的 `trimZero()`；
- 盘口的 `price`、`size` 是 SO 输出字符串，必须原样显示；
- 保存参数时可以转数值校验，但构造 SQL 数据时应避免科学计数法造成精度不可读；
- ID、毫秒时间戳、计算序号不能使用去尾零逻辑。

## 9. 菜单和权限

在“回测中心”下新增“体育市场策略”分组，包含：

```text
体育市场策略
├── 体育市场配置   backtest/sports_config/index
├── 体育市场信息   backtest/sports_market/index
└── 体育铺单历史   backtest/sports_placement/index
```

菜单脚本还要授权以下非菜单动作节点：

```text
backtest/sports_config/add
backtest/sports_config/edit
backtest/sports_config/delete
backtest/sports_market/detail
backtest/sports_market/export
backtest/sports_market/saveParam
backtest/sports_market/saveHistorySetting
backtest/sports_placement/detail
backtest/sports_placement/export
```

建议权限拆分：

- 查看权限：三个 index/detail/export；
- 配置管理权限：add/edit/delete；
- 运行参数权限：sports_market/saveParam。
- 铺单历史保存开关权限：sports_market/saveHistorySetting。

不要默认把参数编辑授权给所有后台角色。`saveParam` 会直接改变下一轮策略输入，应只授予回测管理员或策略研发角色。

修改 `scripts/menu_backtest.sql` 时，应使用精确 node/title 定位体育节点，避免按“回测中心”标题全局删除其他模块菜单。现有脚本重建整棵菜单的逻辑应一并收敛为精确、可重复执行的初始化逻辑。

## 10. CSV 导出

体育市场和体育铺单历史分别提供 CSV 导出：

- 复用当前页面筛选条件；
- 使用 `chunk(200, ...)` 分块读取；
- 输出 UTF-8 BOM；
- 长 ID、毫秒时间戳和类似编号的字符串加制表符保护，防止 Excel 科学计数；
- JSON 使用数据库原始文本；
- 市场导出不默认包含完整 `input_payload/output_payload`，避免文件过大；
- 历史导出可提供 `include_payload=1` 的显式选项。

文件名建议：

```text
sports_market_YYYYmmddHHMMSS.csv
sports_placement_YYYYmmddHHMMSS.csv
```

## 11. 安全与一致性

- 所有写接口声明 `@auth true` 并配置节点权限；
- 所有 ID 强制转正整数；
- 查询筛选使用查询构造器，不拼接 SQL；
- 字段名只能来自服务端白名单，绝不接受请求中的任意 column；
- 删除使用事务及二次确认；
- 参数编辑限制市场状态，并在 SQL update 中重复状态条件；
- 配置表 JSON 必须服务端重新编码；
- 页面输出 JSON 时避免 `raw`；
- 不在页面或日志中展示数据库密码；
- `database-local.yaml` 仅用于本地环境，不提交真实生产凭据。

## 13. 本地联调方案

### 13.1 前置条件

1. `conf/database-local.yaml` 的 `db_f_backtest` 指向本地 `fgmm_f_backtest`；
2. 已创建三张体育表并插入示例配置；
3. MIS 使用 local 环境启动；
4. Go 回测服务仅启用 `sports_market`；
5. 示例体育 SO 文件可加载。

Go 服务启动示例：

```bash
BACKTEST_ENABLED_STRATEGIES=sports_market \
MACHINE_NAME=fgmm-f-backtest-0 \
go run ./cmd/fgmm-f-backtest
```

### 13.2 核心联调用例

#### 用例一：配置生成市场

1. 后台新增体育配置并启用；
2. 等待 `market_generate`；
3. 配置列表显示“已生成”；
4. 市场页出现且只有一条对应 outcome；
5. 市场八个平台参数等于配置初始值。

#### 用例二：持续铺单

1. 使用 live 模式并让报价窗口覆盖当前时间；
2. 市场 `calc_seq` 持续递增；
3. 最新盘口和计算时间自动刷新；
4. 体育铺单历史按每轮增加；
5. 详情 Primary/Mirror 与数据库 JSON 一致。

#### 用例三：运行参数修改

1. 在市场详情记录当前 `calc_seq`；
2. 修改 OFI、VPIN、主动买卖量和库存参数；
3. 保存后立即查询 `sports_market`，值不被 Go 旧快照覆盖；
4. 等待下一轮，`input_payload.microstructure` 和 `inventory` 使用新值；
5. 新增的 `sports_placement` 使用新值；
6. 修改前的历史记录保持旧值。

#### 用例四：配置与市场隔离

1. 市场生成后修改配置页的微观初始值；
2. 当前市场参数保持不变；
3. 已有市场和历史记录均保持不变。

#### 用例五：失败展示

1. 构造一次 SO 输入失败或返回非 0；
2. 市场页显示 `calc_code/calc_msg`；
3. 历史页保留失败输入；
4. 盘口为空时详情页不报模板错误；
5. 后续成功帧仍能正常展示。

### 13.3 数据核验 SQL

```sql
SELECT
    id, sports_config_id, market_status, calc_seq,
    micro_ofi, micro_aggressive_buy, micro_aggressive_sell,
    micro_apr, micro_vpin, micro_hhi,
    inventory_net_yes, inventory_max_abs,
    calc_code, calc_msg, calc_time
FROM sports_market;
```

```sql
SELECT
    sports_market_id, calc_seq,
    micro_ofi, micro_vpin,
    inventory_net_yes, inventory_max_abs,
    JSON_EXTRACT(input_payload, '$.microstructure') AS input_microstructure,
    JSON_EXTRACT(input_payload, '$.inventory') AS input_inventory,
    calc_code, calc_time
FROM sports_placement
ORDER BY sports_market_id, calc_seq;
```

## 14. 验收标准

1. 体育页面不影响现有快盘配置、市场、铺单和对冲页面；
2. 配置 CRUD 字段完整，非法时间、库存和 JSON 无法提交；
3. 一个配置最多对应一条 `sports_market`；
4. 市场详情正确展示基本信息、Primary/Mirror、输入、诊断和原始载荷；
5. 八个平台参数可在 active/pending 市场编辑，且下一轮生效；
6. 参数编辑不会被 Go 的旧快照覆盖；
7. 参数修改前后的 `sports_placement` 各自保存当轮真实值；
8. 历史页面只读，失败快照可追溯；
9. 自动刷新、筛选、分页和 CSV 导出正常；
10. 查看、配置管理和运行参数修改权限可以分别控制；
11. 本地 `database-local.yaml` 可完成全链路联调；
12. 删除失败时事务完整回滚，不留下孤儿数据。

## 15. 实施注意事项

- 当前模拟 `SnapshotSource` 仍从配置的 `source_config` 决定来源名称和 margin；配置编辑后会影响后续输入，但概率等模拟值由 Go 代码提供；
- `sports_market` 是最新快照，不要期望每轮增加行数；每轮增加的是 `sports_placement`；
- history 模式的 `history_start = history_end` 时只会产生一条历史记录；后台提示应说明该行为；
- 市场状态进入 `close` 后不会继续铺单，参数编辑按钮应隐藏；
- 配置编辑不会自动重开已关闭市场；
- 后续从 Mock 切换 Kafka 时，后台三页的数据结构和参数编辑语义不需要变化。
